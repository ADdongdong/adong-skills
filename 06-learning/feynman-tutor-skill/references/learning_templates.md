# 可重用教学模板

## 设计目的

不同输入源、不同学科类型的教学侧重点不同。本文件定义可组合的"教学原子"，让内核按实际情况选择模板，而非所有学科走完全一样的路。

---

## 维度一：按输入源拆分开场模板

| 输入源 | 开场模板 | 差异点 |
|---|---|---|
| `concept_name` | 直接进入目标分级 → 模块计划 | 最快路径 |
| `github_repo` | 先解析仓库 → 提取核心概念 → "已解析 N 个文件，拆为 M 个模块" → 模块计划 | 需要代码理解能力 |
| `uploaded_file` | 先解析文件 → 提取知识结构 → 模块计划 | 需要文件解析能力 |

三种输入源最终都汇入同一条教学循环，但开场处理逻辑不同。

### 输入源异常降级

- `github_repo` 解析失败 → 降级为 `concept_name`，让用户口述要学的概念
- `uploaded_file` 解析失败 → 降级为 `concept_name`，让用户口述要学的概念
- 降级时需告知用户："文件解析遇到问题，我们换个方式——你直接告诉我你想学什么概念"

## 维度二：按学科类型拆分教学侧重点

| 学科类型 | 教学侧重 | 评估方式倾向 | 类比来源 |
|---|---|---|---|
| `hard_skill`（编程/数学/工程） | 机制理解 + 推导过程 | 变式题（换参数/换场景） | 物理世界类比 |
| `soft_skill`（沟通/设计/管理） | 场景判断 + 权衡取舍 | 情境题（给你一个场景你怎么做） | 人际交往类比 |
| `domain_knowledge`（投行/医疗/法律） | 概念边界 + 业务流程 | 案例分析题 | 行业实务类比 |

### 学科类型判断规则

内核在收到学习主题后，按以下规则自动判断学科类型：

- 包含编程/算法/数学/物理/工程关键词 → `hard_skill`
- 包含沟通/设计/管理/协作/面试关键词 → `soft_skill`
- 包含行业/业务/法规/流程/合规关键词 → `domain_knowledge`
- 无法判断时 → 询问用户"这个概念你更偏理论推导、场景判断、还是业务流程？"

### 教学侧重点详解

**hard_skill**：
- 类比来自物理世界（下山找最低点、水流找路径、齿轮传动）
- 评估核心：能否推导"为什么这样"，能否在换参数后正确预测结果
- 补强策略：换参数重算、画图辅助（讲解时即按 P8 主动配图，不仅考砸后补救）

**soft_skill**：
- 类比来自人际交往（相亲第一次见面、请客吃饭点菜、团队分工）
- 评估核心：能否在给定场景中做出合理判断，能否说明权衡逻辑
- 补强策略：换场景重判、对比两个相似场景的差异

**domain_knowledge**：
- 类比来自行业实务（快递分拣、银行柜台流程、餐厅后厨分工）
- 评估核心：能否说清概念边界（A 和 B 的区别），能否走完一遍业务流程
- 补强策略：走流程图（按 P8 主动配图，Mermaid 优先）、对比易混淆概念

## 维度三：教学原子函数

把状态机的每个节点行为抽象成可复用的"函数"：

| 原子函数 | 输入 | 输出 | 复用场景 |
|---|---|---|---|
| `open_with_analogy` | 概念名 + 学科类型 | 类比讲解 | LECTURE 节点 |
| `probe_prereq` | 概念名 | 探针题 + 前置概念ID | 进入新概念前 |
| `assess_output` | 用户回答 + 概念ID | 评估结果(pass/fail) + 根因 | ASSESS 节点 |
| `diagnose_root_cause` | 评估失败结果 | 根因分类 | DIAGNOSE 节点 |
| `remediate_loop` | 根因 + 概念ID | 补强动作（换类比/插微课/换题型） | REMEDIATE 节点 |
| `archive_module` | 概念ID + 掌握度 | before/after 对比 + 归档 | MODULE_DONE 节点 |
| `practice_applied` | 概念ID + 目标等级 + 已学知识范围 | PRACTICE 场景或跳过决策 | PRACTICE 节点 |

---

## 组合逻辑

```
输入源模板（选1）→ 学科类型模板（选1）→ 教学原子组合（按状态机调用）
```

### 示例：教"梯度下降"

```
concept_name 输入
  → hard_skill 类型
  → open_with_analogy（物理世界类比：下山找最低点）
  → probe_prereq（检测是否懂导数/偏导数）
  → assess_output（变式题：换学习率参数，问 loss 怎么变）
  → ...（依状态机流转）
```

### 示例：教"用户访谈"

```
concept_name 输入
  → soft_skill 类型
  → open_with_analogy（人际类比：相亲第一次见面）
  → probe_prereq（检测是否懂开放式问题 vs 封闭式问题）
  → assess_output（情境题：给你一个用户场景你怎么问）
  → ...（依状态机流转）
```

### 示例：教"债券簿记建档"

```
concept_name 输入
  → domain_knowledge 类型
  → open_with_analogy（行业实务类比：拍卖会竞价）
  → probe_prereq（检测是否懂债券定价基本逻辑）
  → assess_output（案例分析题：给定发行场景判断定价方式）
  → ...（依状态机流转）
```

**核心原则：不同领域不走完全一样的路，按学科特性调整类比来源、评估方式、补强策略。**

## 维度四：PRACTICE（做中学）模板

### 触发条件

PRACTICE 节点位于 ASSESS（通过）和 MODULE_DONE 之间，带两个触发条件：

```
ASSESS 通过
  → 检查条件 1：目标是否处于最浅级（L1）？
      ├─ 是 → 跳过 PRACTICE → MODULE_DONE
      └─ 否（中间级或最高级）→ 检查条件 2：PRACTICE 场景是否需要未学过的前置知识？
              ├─ 是（需要额外前置）→ 跳过或简化场景 → MODULE_DONE
              └─ 否（只需已学知识）→ 进入 PRACTICE → MODULE_DONE
```

**条件 2 的判断逻辑**：内核在设计 PRACTICE 场景时，先自检"这个场景需要用户懂哪些东西"——如果都在已学范围内，就上；如果有未学的，要么简化场景（砍掉需要额外前置的部分），要么直接跳过。

**宗旨：保证学习曲线平滑、梯度平缓、稳扎稳打，不在松软地基上盖二楼。**

### PRACTICE 难度分层

| 相对位置 | PRACTICE 形式 | 特征 |
|---|---|---|
| 中间级（L2 … L(n-1)） | 轻量版：情境判断题 | 给真实场景让你判断"该不该用""怎么用"，说出理由 |
| 最高级（Ln） | 重量版：设计/推导任务 | 给目标让你设计方案，需要推导和权衡 |

**纯聊天环境限制**：在 WorkBuddy 聊天里，PRACTICE 只能做轻量版（给场景让你判断/分析）。重量版需要宿主提供代码执行环境。

### 学科差异化 PRACTICE 模板

**hard_skill（编程/数学/工程）**：
- 场景形式：给一个真实参数/配置，让你预测结果或判断该用什么策略
- 例（梯度下降）：给你学习率 α=0.5 和 α=0.01 两组参数，问"哪组更可能震荡，为什么？"
- 例（正则化）：给你一个过拟合的场景，问"你选 L1 还是 L2，为什么？"
- 答错处理：不降级到概念题重来，而是给提示再试一次（PRACTICE 的目的是"用"，不是"考"）

**soft_skill（沟通/设计/管理）**：
- 场景形式：给一个真实工作场景，让你判断"你会怎么做"并说明权衡逻辑
- 例（用户访谈）：给你一个产品调研场景和用户类型，问"你会怎么设计访谈问题，开放式还是封闭式？"
- 例（需求评审）：给你一个有问题的需求文档片段，问"你会怎么提出质疑？"
- 答错处理：给一个更好的做法对比，让用户自己发现差异

**domain_knowledge（投行/医疗/法律）**：
- 场景形式：给一个真实业务案例，让你判断流程/合规性/方案选择
- 例（债券簿记建档）：给你一个发行场景，问"这个场景该用定利率还是定价格？为什么？"
- 例（函证业务）：给你一个函证回函不符的场景，问"你会怎么处理？"
- 答错处理：走一遍正确流程，让用户对比自己的判断

### PRACTICE 设计自检清单

设计 PRACTICE 场景时，内核必须自检：

1. [ ] 这个场景只需要已学概念 + 常识，不需要额外前置知识？
2. [ ] 场景足够具体、真实，不是抽象理论题？
3. [ ] 场景的难度与相对位置匹配（中间级 轻量 / 最高级 重量）？
4. [ ] 答错不会"惩罚"，而是给提示再试或对比学习？

任一条不满足 → 简化场景或跳过 PRACTICE。

## 维度五：学科阶梯表（掌握深度本族化）

节点 2 的目标分级、节点 1.5 的上下文推断、节点 7 的 PRACTICE 难度、节点 8 的归档标签，都依据本表决定"深度档叫什么"。底层「通用深度引擎」只认整数深度 1..n 与相对位置（最浅/中间/最高），本表只提供每学科的本族命名。

### 约束
- 级数范围：每学科 **3~5 级**（下限 3、上限 5，由学科认知层级丰富度决定）。
- 相对位置映射（唯一 PRACTICE 规则）：最浅级(L1) → 跳过 PRACTICE；中间级(L2…L(n-1)) → 轻量版；最高级(Ln) → 重量版。
- 粒度：按「学科」一级建梯，不拆子领域。
- 兜底：表中未列出的学科，agent 按 `hard/soft/domain` 类型直接提议一套阶梯（参考同类型已有学科），无需用户每次确认。

### 增加新学科
新增学科时，在表中追加一行：`{学科名, 类型(hard/soft/domain), 级数(3~5), 各级本族词}`。无需改内核逻辑——引擎只认整数深度与相对位置。

## 维度六：代码学习闭环（代码仓库输入时启用）

当输入源是 **GitHub 仓库 / 本地代码仓库**（代码类学习）时，教学流程升级为「代码学习闭环」：读源码定向（架构→入口→模块→调用链）→ 模块计划标注大作业 → 概念级循环保留 → 模块级大作业（动手实验）→ 双轨归档 → 分支收尾。

完整规范见 `references/code_learning_loop.md`（四态判定、分支机制、作业模板、降级、安全约束）。本维度与维度一（输入源）、维度二（学科类型）、维度五（学科阶梯）**正交**：代码学习闭环管"怎么学项目"，学科阶梯管"深度档叫什么"，学科类型管"怎么教"。
