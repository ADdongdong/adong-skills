# 项目初始化工作流

## 概述

从零开始创建一个 PM 项目，通过引导式对话提取产品愿景、需求和路线图，
建立 `.planning/` 目录结构。

## 前置条件

- 用户提供了产品名称或描述
- 确认工作目录（如有 git repo，在 repo 根目录）

## 执行步骤

### 步骤 0：环境检测

1. 使用 `ls` 检查 `{workspace}/.planning/` 是否存在
2. 如存在：
   - 展示已有项目信息（读取 PROJECT.md 标题）
   - 使用 `AskUserQuestion` 提供选项：
     - "重新初始化（覆盖已有文件）"
     - "合并（保留已有文件，仅补充缺失）"
     - "取消"
3. 如不存在：继续步骤 1

### 步骤 1：引导式提问（BLOCKING loop）

**目标**：充分理解产品想法，而不是收集需求清单。

参考 `references/questioning.md` 的提问策略。

**第一轮 — 开放式提问**：
```
感谢你选择 pm-skill！让我们开始构建你的产品。

首先，用你自己的话告诉我：你想做什么产品？它解决什么问题？
```

**后续轮次 — 追加深度的关键问题**（每次 ≤ 4 个）：

1. **用户 & 问题**: "谁是目标用户？他们现在怎么解决这个问题的？"
2. **核心价值**: "如果用一句话描述核心价值主张，会是什么？"
3. **成功标准**: "产品上线后，怎么判断它成功了？"
4. **约束条件**: "有什么已知的限制？时间、平台、合规、预算？"
5. **竞品环境**: "市面上有类似产品吗？差异在哪？"
6. **技术偏好**: "有技术栈偏好吗？还是完全开放？"

**循环规则**：
- 每次 ≤ 4 个问题
- 跟随用户回答的线索深入，不要按检查表走
- 挑战模糊表述："你说的'好用'具体指什么？"
- 将抽象变具体："'提高效率'—从多少提高到多少？"
- 当你有清晰的心智模型后，进入总结

**反模式（禁止）**：
- ❌ 检查表式提问（"接下来是第3个问题..."）
- ❌ 预设问题清单（不问"你还想补充什么？"这种空洞问题）
- ❌ 匆忙结束（用户刚说两句就总结）
- ❌ 浅层接受（用户说"用户体验好"就过了，不问"具体好在哪里？"）

**总结模板**（提问充足后展示）：
```
## 产品理解总结

**产品**: {name}
**一句话描述**: {elevator pitch}
**目标用户**: {user segments}
**核心痛点**: {pain points}
**解决方案**: {solution approach}
**成功指标**: {key metrics}
**约束条件**: {constraints}
**竞品环境**: {competitive landscape}

以上理解准确吗？还需要补充或修正什么？
```

**STOP and WAIT** — 用户确认后才进入步骤 2。

### 步骤 2：需求提取

将确认的产品理解分解为需求：

1. 列出所有功能需求（用户能感知的能力）
2. 列出非功能需求（性能、安全、合规等）
3. 使用 `references/questioning.md` 的分类方法：
   - **V1（MVP）**: 核心差异化功能，必须上线
   - **V2（后续）**: 增强和完善，V1 之后
   - **不做（Out of Scope）**: 明确排除，防止范围蔓延

展示需求分类 → 等待用户确认。

### 步骤 3：路线图创建

1. 读取 `templates/ROADMAP.md` 了解路线图结构
2. 根据产品规模和 granularity 设置创建阶段：
   - **coarse (3-5 阶段)**：发现 → 策略+PRD → 执行+发布
   - **standard (5-8 阶段)**：发现 → 策略 → PRD → 执行 → 发布
   - **fine (8-12 阶段)**：细分每个阶段（如：用户研究、竞品分析、策略画布、PRD-用户端、PRD-管理端...）
3. 每个阶段包含：
   - **目标**: 这个阶段要达成什么？
   - **成功标准**: 怎么判断完成了？
   - **依赖**: 依赖哪些前置阶段？
   - **预计产出**: 具体文件

4. 展示路线图 → **STOP and WAIT** for user confirmation

### 步骤 4：初始化 .planning/ 目录

用户确认路线图后，创建：

```bash
mkdir -p .planning/phases
```

然后创建以下文件（遵循对应模板）：

1. **PROJECT.md** — 遵循 `templates/PROJECT.md`：
   - 产品名称、愿景、核心价值
   - 目标用户
   - 需求摘要（V1/V2/Out of Scope）
   - 约束条件
   - 关键决策记录

2. **REQUIREMENTS.md** — 遵循 `templates/REQUIREMENTS.md`：
   - 功能需求（含优先级和可追溯性）
   - 非功能需求
   - 用户故事（如有）
   - 需求-阶段映射表

3. **ROADMAP.md** — 遵循 `templates/ROADMAP.md`：
   - 阶段概览
   - 每个阶段的详细信息（目标、成功标准、产出）
   - 进度追踪表

4. **STATE.md** — 遵循 `templates/STATE.md`（< 100 行）：
   - 当前阶段位置
   - 最近决策
   - 待处理事项
   - 会话连续性信息

5. **config.json** — 从 `templates/config.json` 复制：
   - 填入 `project.name` 和 `project.description`
   - 保留默认设置（用户可通过 `/pm-config` 修改）

### 步骤 5：初始化完成

展示总结：

```
✅ PM 项目 "{name}" 初始化完成！

📁 .planning/ 目录已创建：
  - PROJECT.md     产品项目简介
  - REQUIREMENTS.md 产品需求
  - ROADMAP.md      产品路线图
  - STATE.md        项目状态
  - config.json     PM 工作流配置

📋 路线图包含 {N} 个阶段：
  1. {phase-1-name}
  2. {phase-2-name}
  ...

🚀 下一步：/pm-plan 1 开始第一阶段规划
```

## 关键规则

- 步骤 1 是循环的：直到理解清晰才进入总结
- 步骤 1 总结后 BLOCKING：必须等用户确认
- 步骤 3 路线图展示后 BLOCKING：必须等用户确认
- 所有输出使用中文
- 文件创建使用 Write 工具
- PROJECT.md 的产品名称如用户未指定，从描述中推断
