# 需求管理工作流

## 概述

管理产品需求的完整生命周期。**核心原则**：
- **只抽取，不脑补** — 来源有什么就提取什么，缺失字段标记出来让用户补
- **入库即干净** — 新增需求必须通过去重检查 + 冲突检测 + 状态校验，三者全部通过才能入库

## 前置条件

- `.planning/` 目录存在（至少 PROJECT.md + REQUIREMENTS.md）
- 可选：llm-wiki-skill 已安装（启用台账存储和语义检索）

---

## 子工作流

### A. generate — 需求提取 & 入库（严格模式）

#### 步骤 0：检测环境

同前述，检测 wiki 可用性。

#### 步骤 1：读取来源内容

根据 `source-type` 加载来源内容。来源内容即为非结构化文本，不做任何预处理。

#### 步骤 2：识别需求意图 & 逐条结构化

严格遵循 `references/requirement-extraction.md` 的三不原则：
**不脑补、不推断、不跳过**。

对每条识别到的需求意图，执行结构化：

```
需求 #{N}
├── 标题: [从原文提炼，不扩大不缩小]
├── 描述: [仅从原文抽取]
├── 用户价值: [原文有 → 引用] [原文无 → [待确认]]
├── 优先级: [原文有明确强度 → 抽取+标注依据] [原文无 → [待确认]]
├── 验收标准: [原文有 → 引用] [原文无 → [待确认]]
└── 原文引用: "<-- 必须附上"
```

#### 步骤 3：完整性校验（强制）

对每条候选需求，逐字段检查：

| 检查项 | 通过条件 |
|--------|---------|
| 标题 | 准确反映原文意图，未扩大未缩小 |
| 描述 | 全部来自原文，无自行补充内容 |
| 用户价值 | 原文中有明确依据 |
| 优先级 | 原文中有明确强度信号 |
| 验收标准 | 原文中有提及（通常缺失，标记待确认） |
| 原文引用 | 已附上精确的来源引用 |

**任何关键字段（标题/描述/用户价值/优先级）缺失 → 归入 B 组（需补充）**

#### 步骤 4：展示 & 确认 — 分组展示（BLOCKING gate 1）

```
## 需求提取结果

📊 从 {source-type} 提取到 {N} 条候选需求

### ✅ 可直接入库（{M} 条）— 所有关键字段已确认
| # | 标题 | 优先级 | 用户价值 | 依据 |
|----|------|--------|----------|------|
| 1 | {title} | P1（原文"这个必须要有"）| 高 — "{原文}" | "{quote}" |

### ⚠️ 需要你补充信息（{K} 条）— 关键字段缺失
| # | 标题 | 缺失字段 | 已知内容 |
|----|------|----------|----------|
| 2 | {title} | 用户价值、优先级 | 描述: {已抽取内容} |
| 3 | {title} | 验收标准 | 描述: {已抽取内容} |

请选择处理方式:
- "补充 B 组需求" → 逐条向你确认缺失字段
- "仅入库 A 组" → B 组暂存，稍后处理
- "全部暂存" → 所有候选需求不入库，保存为草稿
```

**对 B 组需求，使用 `AskUserQuestion` 逐条确认缺失字段。不自行填补。**

#### 步骤 5：去重检查 + 冲突检测 + 状态校验（强制，BLOCKING gate 2）

**仅对 A 组（用户确认可入库的）执行，三条全部通过才能入库：**

**5.1 去重检查（必须通过）**：
```
对每条待入库需求:
1. 标题匹配: 在 REQUIREMENTS.md 中搜索相似标题
2. 语义检索: wiki query（如可用）
3. 相似度 ≥ 85% → 标记疑似重复 → 展示对比 → 等待用户决策
4. 相似度 60-84% → 标记为可能关联 → 询问用户（合并/关联/独立）
5. 无匹配 → ✅ 通过
```

**5.2 冲突检测（必须通过）**：
```
对每条待入库需求:
1. 检查是否与已有需求存在逻辑矛盾（功能互斥、范围矛盾）
2. 检查依赖的需求是否存在且状态正常（非 cancelled）
3. 有冲突 → 🚩 展示矛盾点 → 等待用户决策
4. 无冲突 → ✅ 通过
```

**5.3 状态校验（必须通过）**：
```
对每条待入库需求:
1. 状态默认为 pending（待评审）
2. 检查无异常状态标记
3. 检查来源文件存在且可追溯
4. ✅ 通过
```

**三条全部通过的需求 → 进入入库步骤。任一条未通过 → 必须用户决策后才能继续。**

#### 步骤 6：写入台账（仅通过校验的需求）

同前述，写入 wiki entities + 更新 REQUIREMENTS.md。

#### 步骤 7：生成摘要

```
✅ 需求提取完成

入库: {M} 条（REQ-XXX ~ REQ-YYY）— 已通过去重/冲突/状态三重校验
待补充: {K} 条 — 关键字段缺失，已暂存
合并: {P} 条 — 合并到已有需求
冲突: {J} 条 — 已记录，待用户决策
跳过: {S} 条

📋 查看: /pm-req list
🔍 调研: /pm-req research <id>
```

### B. list — 需求列表查看

#### 步骤 1：加载需求数据

1. 读取 `REQUIREMENTS.md` → 解析需求可追溯性矩阵
2. 如 wiki 可用 → `wiki query "列出所有需求实体"` 获取最新状态

#### 步骤 2：应用筛选

按传入参数筛选（`--status`、`--priority`、`--source`）。

#### 步骤 3：展示

按状态分组展示需求列表（pending → researching → planned → in-dev → done），
包含统计摘要和关键字段。

---

### C. show — 需求详情

#### 步骤 1：定位需求

1. 在 `REQUIREMENTS.md` 中找到 REQ-XXX 的行
2. 如 wiki 可用 → 读取 `wiki/entities/REQ-XXX.md` 获取完整详情

#### 步骤 2：展示

展示完整需求信息：状态、优先级、来源、描述、用户故事、
验收标准、关联需求、冲突、调研记录、变更历史。

---

### D. update — 状态更新

#### 步骤 1：定位需求

同 show。

#### 步骤 2：更新状态

1. 更新 wiki entity 的 frontmatter `status` 和 `updated`（如 wiki 可用）
2. 更新 `REQUIREMENTS.md` 中对应行的状态和验证日期
3. 记录变更历史（追加到 wiki entity 的 `## History` 部分）

#### 步骤 3：确认

```
✅ REQ-XXX 状态更新: {old-status} → {new-status}
   备注: {用户备注或自动备注}
```

---

### E. research — 需求针对性调研

#### 步骤 1：加载需求上下文

1. 读取需求详情（描述、用户故事、验收标准、关联需求）
2. 了解该需求在产品中的定位（关联哪个阶段/PRD）

#### 步骤 2：多维度调研

**2.1 竞品功能调研**：
- `WebSearch "{需求关键词} 竞品实现"`
- 搜索 3-5 个竞品在该功能上的做法
- 输出：竞品方案对比（功能完整度、用户体验、技术方案）

**2.2 用户需求验证**：
- `WebSearch "{需求关键词} 用户痛点 需求"`
- 搜索用户对该功能的讨论、评价、期望
- 输出：用户需求强度评估

**2.3 可行性分析**：
- `WebSearch "{需求关键词} 实现方案 最佳实践"`
- 如有 wiki → `wiki query "{需求关键词} 技术方案"`
- 输出：方案选项 + 推荐方案 + 风险点

#### 步骤 3：生成调研报告

创建 `REQ-XXX-RESEARCH.md`（在阶段目录或 wiki entities 目录）：

```markdown
# REQ-XXX 需求调研报告

## 调研概要
- 需求: {title}
- 调研日期: {date}
- 调研人: AI (pm-skill)

## 竞品参考
| 竞品 | 实现方式 | 优势 | 不足 | 参考价值 |
|------|----------|------|------|----------|
| {name} | {approach} | {pros} | {cons} | {参考什么} |

## 用户需求验证
- 需求强度: {高/中/低} — {依据}
- 用户期望: {insights}

## 可行性分析
- 方案 A: {描述} — 优/缺点
- 方案 B: {描述} — 优/缺点
- 推荐: {方案 + 理由}

## 差异化机会
- {竞品未满足的需求点}

## 建议
- 纳入阶段: Phase {N}
- 建议优先级: {P0/P1/P2}
- 风险点: {risks}

## 来源
- {URLs}
```

#### 步骤 4：更新需求状态

- 如当前状态为 `pending` → 更新为 `researching`
- 记录调研日期和调研报告路径

---

### F. dedup — 全量去重

#### 步骤 1：加载所有需求

从 `REQUIREMENTS.md` 和 wiki entities 加载全量需求列表。

#### 步骤 2：逐对比较

对每对需求计算相似度：
- 标题相似度（Levenshtein / token overlap）
- 描述语义相似度（wiki 语义检索，如可用）
- 功能范围重叠度（关键词集合 Jaccard）

#### 步骤 3：展示疑似重复

列出相似度 ≥ 阈值（默认 70%）的需求对，按相似度降序排列。

#### 步骤 4：用户处理

用户逐对决策：合并、标记为父子关系、标记为独立、忽略。

---

## 关键规则

- 需求提取 → BLOCKING gate 用户确认后才入库
- 去重不自动合并，冲突不静默覆盖
- 每条需求标注来源，保持端到端可追溯
- Wiki 不可用时自动降级，不阻塞工作流
- 状态变更记录时间和备注
- 中文输出
