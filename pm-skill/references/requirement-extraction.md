# 需求提取模式参考

> 本文档定义从非结构化来源中**严谨提取**产品需求的策略。
> **核心原则：只抽取明确信息，缺失字段标记待确认，不脑补任何内容。**

---

## 核心原则

### 三不原则

| 原则 | 说明 | 反例 |
|------|------|------|
| **不脑补** | 来源没说的内容，绝不自己填充 | ❌ 用户说"要登录功能"，你补充"支持指纹登录" |
| **不推断** | 来源暗示但不明确的内容，标记待确认 | ❌ 用户说"要快"，你推断为"3秒内响应"并直接填入 |
| **不跳过** | 关键字段缺失时，必须标记并让用户确认 | ❌ 用户说"做导出功能"，你自行补全验收标准后直接入库 |

### 必须确认的关键字段

每条候选需求至少需包含以下字段才能入库，缺失任一项 → 标记 `[待确认]`：

| 字段 | 必要性 | 可以从来源抽取吗？ |
|------|--------|-------------------|
| **标题** | 必须 | ✅ 从原文提炼一句话概括 |
| **描述** | 必须 | ✅ 从原文抽取具体内容 |
| **产品** | 必须 | ✅ 从当前项目上下文获取（PROJECT.md） |
| **端** | 必须 | ⚠️ 仅当来源明确提及时可抽取，否则标记待确认 |
| **功能模块** | 必须 | ⚠️ 仅当来源明确提及时可抽取，否则标记待确认 |
| **需求类型** | 必须 | ⚠️ 可根据描述推断（如"支持XX"→feature，"优化XX"→optimization），但需用户确认 |
| **优先级** | 必须 | ⚠️ 仅当来源有明确强度信号时可抽取，否则标记待确认 |
| **来源** | 必须 | ✅ 由 source-type 参数确定 |
| **来源详情** | 必须 | ✅ 由 source-type 参数 + 文件路径确定 |
| **验收标准** | 建议 | ⚠️ 通常需要用户补充 |

## 提取流程

### 步骤 1：从非结构化文本中识别需求

扫描来源内容，识别**所有明确表达的需求意图**。

**信号词**（仅当上下文确认为需求意图时）：

| 模式 | 示例 | 置信度 |
|------|------|--------|
| 「需要/要/得…」 | "用户需要能离线使用" | 高 — 明确需求 |
| 「不支持/缺少/没有/无法…」 | "目前无法批量删除" | 高 — 明确缺口 |
| 「XX 是问题/痛点」 | "手动整理是最花时间的" | 中 — 暗示需求 |
| 「希望能/最好能…」 | "希望能导出 PDF" | 中 — 软性需求 |

**不视为需求的情况**：
- 纯技术讨论（"用 Redis 做缓存"）
- 闲聊或主观评价（"竞品 X 的 UI 真好看"）
- 未形成明确功能点的一般性讨论

### 步骤 2：逐条结构化

对每个识别到的需求意图，执行结构化：

```
需求 #{N}
├── 标题: [从原文提炼，10 字以内]
├── 描述: [从原文抽取，1-2 句]
├── 产品: [从 PROJECT.md 获取当前产品名]
├── 端: [原文有 → 直接引用] [原文无 → [待确认]]
├── 功能模块: [原文有 → 直接引用] [原文无 → [待确认]]
├── 需求类型: [根据描述推断 + 标注依据] [原文无 → [待确认]]
├── 优先级: [原文有明确强度 → 抽取 + 标注依据] [原文无 → [待确认]]
├── 来源 + 来源详情: [由 source-type 和文件路径确定]
├── 验收标准: [原文有 → 直接引用] [原文无 → [待确认]]
└── 原文引用: "<-- 必须附上来源原文，保证可追溯"
```

**严禁的行为**：
- ❌ 原文说"要登录"，你结构化出"支持手机号+邮箱+微信三种登录方式"
- ❌ 原文说"要快"，你填入"响应时间 < 2 秒"
- ❌ 原文没提用户价值，你写"高 — 提升用户体验"
- ❌ 原文没提优先级，你自行标 P1

### 步骤 3：完整性校验

对每条结构化后的需求，逐字段检查：

```
检查清单:
□ 标题: 是否准确反映原文意图（不扩大、不缩小）？
□ 描述: 是否全部来自原文（无自行补充）？
□ 用户价值: 原文中有依据吗？无 → 标记 [待确认]
□ 优先级: 原文中有明确强度信号吗？无 → 标记 [待确认]
□ 验收标准: 原文中有提及吗？无 → 标记 [待确认]
□ 原文引用: 是否附上了精确的来源引用？
```

### 步骤 4：展示 & 确认（BLOCKING）

将候选需求按完整度分为两组展示：

**A 组 — 可直接入库的（所有关键字段已确认）**：

```
### ✅ 可直接入库 ({N} 条)

**REQ-候选-1**: {标题}
  - 描述: {从原文抽取的内容}
  - 用户价值: {原文依据}
  - 优先级: P1（依据：用户原话"这个必须要有"）
  - 验收标准: {原文提及的标准}
  - 来源: "{原文引用}"
```

**B 组 — 需要补充信息（有关键字段缺失）**：

```
### ⚠️ 需要你补充信息后才能入库 ({M} 条)

**REQ-候选-2**: {标题}
  - 描述: {已从原文抽取的内容}
  - 用户价值: [待确认] — 原文未提及用户价值
  - 优先级: [待确认] — 原文无明确强度信号
  - 验收标准: [待确认]
  - 来源: "{原文引用}"
  
  📝 请补充:
  1. 这个功能解决用户什么痛点？（用户价值）
  2. 不做或延后做的后果是什么？（优先级）
  3. 做成什么样算完成？（验收标准）
```

**对于 B 组需求，必须使用 `AskUserQuestion` 逐条向用户确认缺失字段。**

### 步骤 5：用户确认后汇总

用户补充完毕后，再次展示完整候选列表 → 用户最终确认 → 进入入库流程。

## 按来源类型的特殊处理

### 竞品分析报告

**可抽取的内容**：竞品有但我们计划中没提到的功能 → 标记为"竞品驱动需求"
**容易脑补的场景**：看到竞品有 XX 功能，自动假设我们也需要 → ❌ 必须先确认用户是否认为这是需求
**必须确认**：该功能是否适合我们的产品定位？是否需要差异化？

### 会议纪要

**可抽取的内容**：会议中明确讨论的功能点、决策项
**容易脑补的场景**：从讨论中推断出讨论者"可能想要"的功能 → ❌ 只抽取明确说出的
**必须确认**：讨论型需求（还在探讨）vs 决策型需求（确认要做）

### 用户文字输入

**可抽取的内容**：用户明确描述的功能点
**容易脑补的场景**：用户说"登录"，你补全"手机号登录+微信登录+邮箱登录" → ❌ 只抽取用户说的
**必须确认**：用户说的"登录"具体指哪种方式？需不需要多种？

## 优先级 — 仅当原文明确时可抽取

| 原文信号 | 可抽取优先级 | 依据强度 |
|----------|-------------|----------|
| "必须要有/没有不行/核心/不做产品没法用" | P0 | 强 — 可抽取 |
| "需要/应该/重要" | P1 | 中 — 建议确认 |
| "希望能/如果能/最好有/也不错" | P2 | 弱 — 仍建议确认 |
| 无明确信号 | [待确认] | 必须问用户 |

**禁止**：根据"感觉"或"行业惯例"自行分配优先级。

## 去重判断

对每条候选需求，在入库前执行去重：

1. **标题匹配**：在已有需求列表中搜索相似标题
2. **语义检索**（wiki 可用）：`wiki query "已有需求中是否有关于 {标题} 的记录？"`
3. **判断标准**：

| 相似度 | 判断 | 处理 |
|--------|------|------|
| ≥ 85% | 高度疑似重复 | 展示对比，默认建议合并，等用户决策 |
| 60-84% | 可能相关 | 展示已有需求，询问是合并、关联还是独立 |
| < 60% | 独立需求 | 可正常入库 |

**禁止**：自动合并或静默跳过疑似重复需求。

## 冲突检测

入库前检查新需求是否与已有需求存在逻辑矛盾：

| 冲突类型 | 检测方式 | 示例 |
|----------|----------|------|
| 功能互斥 | 新需求的关键词与已有需求矛盾 | "离线模式" vs 已有"纯在线架构" |
| 范围矛盾 | 限定词冲突 | "仅 iOS" vs 已有"全平台" |
| 依赖缺失 | 新需求依赖一个标记为 cancelled 的需求 | 新需求依赖 REQ-005，但 REQ-005 已取消 |

**检测到冲突 → 必须用户决策后才能继续。禁止静默处理。**
