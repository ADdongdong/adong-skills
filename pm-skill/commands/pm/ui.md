# /pm-ui — UI 原型生成

触发 `pm-skill`，根据产品需求、阶段描述或需求编号生成 HTML 原型。
**设计规范是必选项**——生成的每个像素都必须遵守所选规范。

## 用法

```
# 模式 A：直接描述生成
/pm-ui "登录页面" --design apple

# 模式 B：需求驱动生成（先检索 wiki，确认后再生成）
/pm-ui --req REQ-008 --design apple

# 模式 C：阶段原型生成
/pm-ui "phase-2 仪表盘" --design apple --output prototypes/v2

# 模式 D：调整已有原型
/pm-ui "增加筛选功能" --design apple --adjust prototypes/login.html
```

## 设计规范（必选）

`--design` 参数指向 `design/` 目录下的设计规范文件（不含路径前缀和 `.md` 后缀）：

| `--design` 值 | 对应文件 | 描述 |
|---------------|---------|------|
| `apple` | `design/DESIGN-apple.md` | Apple 风格——摄影优先、SF Pro 字体、单蓝色强调、全幅磁贴布局 |

> **新增规范**：将 `.md` 文件放入 `design/` 目录，即可通过 `--design <文件名不含.md>` 引用。

## 工作流

参考 `workflows/ui-prototype.md`。

### 模式 A：直接描述生成 — 6 个步骤

**Step 1: 加载设计规范**
- 读取 `design/DESIGN-{name}.md`
- 提取所有设计 Token：颜色、字体、圆角、间距、组件规格、阴影、布局规则
- 提取 Do's and Don'ts 作为强制性约束

**Step 2: 解析需求**
- 理解用户描述的功能/页面需求
- 如果是 phase-N，读取对应的阶段文档（PRD、PLAN 等）获取上下文
- 确定需要哪些组件和布局

**Step 3: 组件映射**
- 将需求中的 UI 元素映射到设计规范中的组件
- 如果规范中没有对应组件，基于 Token 构建（遵循 Do's and Don'ts）

**Step 4: 生成 HTML 原型（BLOCKING）**
- 生成独立的、可直接浏览器打开的 HTML 文件
- 所有样式内联（单文件，无外部依赖，CSS 在 `<style>` 中）
- 每个 CSS 值必须来自设计 Token：
  - 颜色：使用规范的 hex 值，不得自创
  - 字体：使用规范定义的 fontFamily、fontSize、fontWeight、lineHeight、letterSpacing
  - 圆角：使用规范定义的 rounded token
  - 间距：使用规范定义的 spacing token
  - 阴影：严格遵守规范（如 Apple 规范只允许一个产品阴影）
- 包含基础交互（hover/active 状态按规范定义）
- 中文优先，英文专业术语保留

**Step 5: 设计合规检查**
- 逐项对照设计规范的 Do's and Don'ts 检查生成的原型
- 列出任何偏差并修正
- **GATE**: 展示原型摘要 → 等待用户确认是否需要调整

**Step 6: 输出**
- 写入 HTML 文件到指定目录（默认 `prototypes/`）
- 返回文件路径和原型摘要

### 模式 B：需求驱动生成（`--req <id>`） — 核心模式

**这是最智能的生成模式。不盲目生成，而是先检索 wiki 获取完整上下文，再让用户决策。**

此模式与 `/pm-req` 需求管理系统和 llm-wiki-skill 深度集成。

#### Step 1: 加载需求

1. 从 wiki 台账读取需求详情：`wiki/entities/{REQ-ID}.md`
2. 如 wiki 不可用，降级读取 `REQUIREMENTS.md` 中的需求条目
3. 提取：需求描述、用户故事、验收标准、优先级、关联功能、状态

#### Step 2: 检索历史上下文（llm-wiki）

**这是关键步骤——在生成任何代码前，先做充分检索。**

**2.1 Wiki 全量检索**（如 llm-wiki-skill 可用）：
- 搜索历史页面/界面：`/wiki-query "页面 界面 原型 {需求关键词}"`
- 搜索相关功能：`/wiki-query "{需求关联功能} 功能模块 页面"`
- 搜索已有原型引用：`/wiki-query "prototype html {需求关键词}"`

**2.2 本地原型检索**（检查已有原型文件）：
- 扫描 `prototypes/` 目录下的 HTML 文件
- 读取每个原型的元数据注释（设计规范、需求描述、关联的需求编号）
- 检查是否有原型已覆盖当前需求的全部或部分功能

**2.3 阶段文档检索**（获取产品上下文）：
- 检查 `.planning/phases/` 下各阶段 PRD 中与需求相关的章节
- 提取已定义的界面结构和交互要求

#### Step 3: 综合 & 决策（BLOCKING Gate #1）

**将所有检索结果综合展示给用户，让用户做决策。**

Agent 展示一份**生成前研究报告**：

```
# REQ-XXX 原型生成前研究

## 1. 需求概要
- 需求: {标题}（{优先级}）
- 用户故事: {用户故事}
- 验收标准: {验收标准}

## 2. 历史相关功能
- wiki 中找到 N 个相关功能模块：...
- wiki 中找到 M 个相关页面引用：...

## 3. 已有原型检查
- ✅ 找到 1 个已有原型覆盖了此需求的 70% 功能: prototypes/xxx.html
  → 建议: 在现有原型上调整
- 或
- ❌ 未找到已有原型覆盖此需求
  → 建议: 创建新原型

## 4. 生成方案（待确认）
- 页面: {页面名称}
- 包含组件: {组件列表，映射到设计规范}
- 布局: {布局结构}
- 关联功能: {需要集成展示的历史功能}

请确认：
  A. 在已有原型上调整（如找到匹配的原型）
  B. 创建新原型
  C. 补充更多信息再生成
```

**此 gate 强制执行——必须等待用户选择后才进入下一步。**

#### Step 4: 执行生成（新建或调整）

根据用户选择进入对应流程：

**选择 A — 调整已有原型**：
- 进入模式 D（调整已有原型）流程
- 在现有原型上增量修改，增加需求对应的功能

**选择 B — 创建新原型**：
- 进入模式 A 的 Step 3-6（组件映射 → 生成 → 合规检查 → 输出）
- 生成时融入 Step 2 检索到的历史功能信息（如相关功能的 UI 模式、已有的交互范式）

**选择 C — 补充信息**：
- 用户在 Gate 处提供了额外信息
- 更新生成方案后，再次展示 → 确认 → 生成

#### Step 5: 输出 & 关联

- 写入原型文件
- 在原型 HTML 注释中记录关联的需求编号
- 可选：反向更新 wiki 需求条目，记录原型文件路径

---

### 模式 C：阶段原型生成

与模式 A 相同，但 Step 2 的输入来源为阶段文档：
- 读取 `.planning/phases/NN-name/NN-PRD.md`
- 读取 `.planning/phases/NN-name/NN-MM-PLAN.md`
- 提取该阶段涉及的所有页面和功能描述

---

### 模式 D：调整已有原型 — 3 个步骤

**Step 1: 加载上下文**
- 读取已有原型 HTML 文件
- 从 HTML 注释中提取元数据（设计规范、需求编号、生成历史）
- 如元数据不可用，要求用户通过 `--design` 指定设计规范

**Step 2: 确认变更（BLOCKING Gate）**
- 展示：当前原型内容摘要 + 用户要求的变更 + 变更影响分析
- **必须等待用户确认后再修改**

**Step 3: 应用变更**
- 在现有 HTML 结构上增量修改
- 新增元素必须遵守原设计规范 Token
- 保持已有内容不变（除非用户明确要求删除）

**Step 4: 输出**
- 原地更新或写入新版本文件
- 标注变更内容

## 产出物

- `prototypes/{name}.html` — 可独立打开的 HTML 原型文件
- 文件内含元数据注释：设计规范名称、生成时间、需求描述、关联需求编号（如有）

---

## 设计 Token 使用规范

生成 HTML 时必须遵守以下优先级：

1. **组件 Token** — 如果 UI 元素匹配规范中定义的组件，直接使用组件的所有属性
2. **基础 Token** — 颜色、字体、圆角、间距——每个值必须可追溯到规范文件中的 Token
3. **推导值** — 仅在规范明确允许推导时使用（如响应式缩放）
4. **禁止自创** — 不得使用规范外的颜色、字体、阴影或圆角值

## 关键规则

- **设计规范是强制性约束**，不是参考建议——所有视觉属性必须来自规范 Token
- **需求驱动模式必须先检索、再确认、后生成**——绝不跳过研究步骤盲目生成
- 生成独立的单文件 HTML（无外部 CSS/JS 依赖，CDN 字体除外）
- 中文输出，英文术语保留
- 每个原型文件包含元数据注释（设计规范名、生成时间、需求描述、关联需求编号）
- 调整模式保持已有内容完整性，确认后再增量修改
- 如设计规范中没有对应组件，基于基础 Token 构建，同时在输出中标注为"自定义组件"
- Blade: 需求编号模式下，如 llm-wiki-skill 不可用，降级使用文件搜索（grep/Glob）替代
