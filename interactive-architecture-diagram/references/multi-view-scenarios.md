# 多视图与 Scenarios

仅当 `SKILL.md` 中的多视图触发条件成立时读取本页。

## 1. 先判断是否真的需要拆分

通常保留单图：

- 只有一个核心问题；
- 节点和关系处于同一抽象层级；
- 弱化次要内容后，主链路仍然清楚。

通常需要拆分：

- 用户同时要求全局架构、模块内部和执行步骤；
- 多个子系统各自拥有独立边界与内部关系；
- 同一套节点上有多条链路，需要逐条聚焦；
- 单图必须混合多个抽象层级或隐藏关键关系才能装下。

不要只按节点数量机械拆分。先尝试收窄主题、弱化次要内容或提高抽象层级。

## 2. 区分 Layers 与 Scenarios

问自己：**每个视图展示的是不同内容，还是同一内容的不同焦点？**

| 用户真正需要的内容 | 机制 | 通俗解释 |
|---|---|---|
| 不同模块、层级或范围，各视图有自己的内容 | `layers` | 像一本书的不同章节 |
| 同一套节点与关系，每次突出不同链路或状态 | `scenarios` | 像在同一张地图上切换路线 |

### Layers 示例

- 系统总览、订单域内部、支付域内部各一个视图；
- 宏观系统地图与微观执行流程分开；
- 前端、后端、数据平台作为独立 Tab 展示。

### Scenarios 示例

- 同一微服务架构分别突出 Query 与 Callback 链路；
- 同一订单系统分别查看创建、取消与退款；
- 同一基础设施分别查看正常路径与故障转移路径。

### 容易混淆的边界

- “总览”与“支付内部细节”使用不同节点集合和抽象层级：选 `layers`。
- “支付成功”与“支付失败”共用绝大多数节点，只改变聚焦路径：选 `scenarios`。
- 两者同时存在时，可先用 `layers` 分范围，再仅在确有多路径的 layer 内使用 scenarios；不要无理由叠加。

## 3. 输出拆分方案

在 `SKILL.md` 要求的确认门中，方案至少包含：

- 机制：`layers` 或 `scenarios`；
- 每个视图的名称；
- 每个视图的聚焦点；
- 每个视图的抽象层级：宏观、中观或微观；
- 拆分理由。

示例：

```text
建议使用 scenarios，因为三个视图共用同一套服务，只需切换聚焦链路：
1. CreateOrder：中观，突出网关→订单→库存→支付。
2. CancelOrder：中观，突出订单→库存释放→退款。
3. Callback：中观，突出支付回调→订单状态更新→通知。
这样可以保持单一架构来源，避免三张图的结构逐渐不一致。确认后我再生成。
```

用户未明确确认前，禁止创建 `input_file` 和调用生成脚本。用户修改方案时重新整理并再次确认。原请求已经明确指定拆分机制与视图内容时，可跳过询问。

## 4. 把意图写进 `# Request`

客户端只用自然语言描述拆分与高亮意图。具体 CW/D2 语法由后端生成，禁止在请求中自行编写或拼接图形语法。

Layers 示例：

```text
拆为三个独立视图：系统总览展示外部参与者与核心域；订单域展示创建、库存锁定和状态流转；支付域展示支付发起、回调和退款。三个视图分别采用宏观、中观、中观层级。
```

Scenarios 示例：

```text
基于同一套完整服务架构提供 CreateOrder、CancelOrder、Callback 三个场景。每个场景淡化无关组件并突出目标链路；所有场景共享同一份基础节点与关系定义。
```

## 5. Scenarios 高级规则

1. **单一数据源**：先维护一份包含全部共用节点和关系的基础图。
2. **增量覆盖**：每个 scenario 只描述相对基础图变化的聚焦效果或状态。
3. **禁止复制整图**：不得为每条链路复制、拼接一份完整架构。
4. **优先弱化而非删除**：淡化无关组件并高亮目标关系，以保留整体上下文。
5. **使用业务化命名**：采用 `CreateOrder`、`Callback` 等名称，避免 `Scenario1`。

如果用户只需要几个完全独立的图，不要误用 scenarios。如果只是希望主图突出一条链路，也不必额外创建 scenario。

## 6. 执行前检查

- [ ] 已说明为什么单图不够。
- [ ] 已按“不同内容 / 不同焦点”选择 layers 或 scenarios。
- [ ] 每个视图的名称、焦点和抽象层级明确。
- [ ] 已取得用户确认，或原请求已明确指定拆分方案。
- [ ] `# Request` 只有自然语言意图，没有手写图形语法。
- [ ] scenarios 共用基础图，没有复制整图。
