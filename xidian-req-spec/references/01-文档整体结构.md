# 01 文档整体结构

## 一、文档级要素（顺序固定）

| 顺序 | 要素 | 说明 |
|---|---|---|
| 1 | 封面 | 空行 ×4 → 系统名 → `需求说明书vX.Y.Z` → 空行 → `西安西点信息技术有限公司` → `YYYY年M月`；右对齐/居中按原文档；样式用"文档日期" |
| 2 | 文档修改历史 | 表：`版本号 \| 修改日期 \| 编写人 \| 评审人 \| 批准人 \| 修改内容`（6 列，第 2 行起填） |
| 3 | 编写说明 | 3 条固定文字，原样保留 ↓ |
| 4 | 目录 | TOC 域，**打开文档即自动按当前正文重排**（置了 `w:updateFields` + `w:dirty`）；模板里缓存的旧条目必须清掉，见 `03-样式与编号规范.md` 第十一节 |
| 5 | H1 菜单目录 | 表：`一级菜单 \| 二级菜单 \| 三级菜单`（行数 = 本系统菜单实际数量） |
| 6 | 正文 | 见下 |

**编写说明（固定 3 条）**
1. 业务部门编写本需求说明文档之前，新增功能需求需要与需求建设部门对需求的描述和验收标准进行过邮件确认。
2. 本文档蓝色斜体字都是注释或举例，供业务人员编写业务需求参考。
3. 本《业务需求说明书》适用于各种不同类型的业务需求。填制时可根据需求的不同情况在下列章节中裁减。

## 二、【菜单目录】维护规则

- 三列表，`一级菜单 / 二级菜单 / 三级菜单`；**同级重复值留空**（合并单元格的视觉效果靠留空实现），例如"项目管理"只在首行写一次，其下二级菜单的第一列留空。
- 菜单命名与正文 H3/H4 一一对应；差异项在菜单名后用括号标注，例如 `各业务条线项目查看（<客户名>）` 表示客户定制菜单、`以<客户名>非信创版本菜单为准` 表示沿用客户既有版本菜单。
- **正文每个功能点都必须能在本表找到落点；表里有而正文没有的，说明需求尚未编写**（这是发现文档缺口的自检手段）。
- **说明性章节不进本表**：`H2 <版本>变化概览`（3.0→4.0 这类升级说明）、`H3 业务流程`（放流程框架图的那类）都**不是菜单**，
  本表里没有它们是正常的。配套约束：这类章节下**不要挂功能点** —— 挂了就会破坏「菜单 ↔ 功能点」的一一对应，
  自检时说不清是漏写还是本来就该没有。

## 三、正文结构（H1 起）

正文按「系统 →（端别）→ 一级功能模块 → 功能点 → 七节」逐层展开。**系统名和端别层都是按需的**：

1. **H1 的系统名按本次开发的功能来定** —— 写成 `<系统名称>标准产品需求`。
   **不要沿用模板来源文档的系统名** —— 本次需求落在哪些系统上，就写哪些系统；涉及两个系统就写两个 H1，
   只涉及一个就只留一个。
2. **端别层（H2）按需，默认不设** —— 只有当同一个系统**跨多个端、且各端需求不同**时才加端别层
   （如 `H2 WEB端需求` / `H2 移动端需求` / `H2 助手端需求` / `H2 客户端需求`）。
   本次开发的功能只落在一个端上（绝大多数情况）→ **整层不要**，一级功能模块直接挂到 H1 下面。
   某个端本期没有需求，**也不写那个端** —— 不留空标题占编号。

### 形态一 · 单端（默认，绝大多数情况）

```
H1 菜单目录          +  表：一级菜单 | 二级菜单 | 三级菜单
H1 <系统名称>标准产品需求
    H2 <版本>变化概览            ← 仅 3.0→4.0 这类大版本升级时写；非功能点，不要挂功能点
    H2 一级功能模块（首页 / ××管理 / ××统计分析 / ××基础维护 / 系统设置 …）
        H3 功能点（页面级）
            H4 业务说明 / 业务规则 / 使用角色 / 权限说明 / 功能说明 / 页面字段说明 / 输入、输出
```

### 形态二 · 多端（同一系统多端并存时才用）

```
H1 <系统名称>标准产品需求
    H2 <端别>需求（WEB端 / 移动端 / 助手端 / 客户端 …）
        H3 一级功能模块
            H4 功能点（页面级）
                H5 业务说明 / 业务规则 / 使用角色 / 权限说明 / 功能说明 / 页面字段说明 / 输入、输出
```

> 一级功能模块下若还有并列页面（"首页"下挂多个报送页这类），在功能点之上再插一层页面层级，
> 七节式随之落到再下一级 —— 见 02 的"三种挂载层级"。

## 四、编号与层级对照（自动编号，勿手写）

**功能点落在第几级，取决于有没有端别层**；七节式永远紧跟功能点的下一级：

| 形态 | H1 | H2 | H3 | H4 | H5 |
|---|---|---|---|---|---|
| **单端**（无端别层，默认） | `<系统名>标准产品需求` | 一级功能模块 | **功能点** | 七节式小节 | — |
| **多端**（有端别层） | `<系统名>标准产品需求` | `<端别>需求` | 一级功能模块 | **功能点** | 七节式小节 |

- 一级菜单本身即功能点（定制化功能需求）→ 功能点落在 H3，与"单端"同层级。
- 一个模块下含多个并列页面 → 模块下再插一层"页面"，七节落到 H6。
- 脚本里用 `req(level=)` 指定**功能点**的层级：单端 `3`、多端 `4`（默认）、定制化功能需求 `3`、多页模块 `5`。
- 编号示例（单端）：`1. 菜单目录` → `2. <系统名>标准产品需求` → `2.1 首页` → `2.1.1 首页－待办处理` → `2.1.1.1 业务说明`
- 编号示例（多端）：`2. <系统名>标准产品需求` → `2.1 WEB端需求` → `2.1.1 首页` → `2.1.1.1 首页－待办处理` → `2.1.1.1.1 业务说明`

## 五、裁剪规则

- **系统**：本次需求涉及几个系统就保留几个 `H1 <系统名>标准产品需求`；只涉及一个就只留一个。
- **端别层**：功能只落一个端 → **不设端别层**（H2 直接是一级功能模块）；
  跨多端 → 设端别层，且**只写本期有需求的端**，没有需求的端整层不写。
- **变化概览**：仅 3.0→4.0 这类大版本升级时写；小版本迭代不写。
- **定制化需求章**：**默认不写**（判断口径见第六节）。
- 裁剪只删章节，**不要改章节名、不要重排顺序、不要手写序号**（序号自动）。

## 六、按需章节：定制化需求（默认不写）

**正文结构里不包含这一章。** 只有该功能**确有特殊定义**、或明确说明为**定制功能**
（客户/项目提出了与标准产品不同的做法，且有书面依据）时，才在正文末尾追加这一章；
否则**整章不写** —— 连「定制化需求引言」「需求总览」一起省，**不留空标题**（空标题会白占一个自动编号）。

**判断顺序**（先往下看，别急着立定制章）：

1. 这条需求能不能**并进对应的标准产品功能点**写？能就并进去（例如"多封函证共用一个快递面单"这类形态差异），**不另立定制章**；
2. 确实放不进去、且属于客户特殊约定 → 才立 `H1 定制化需求`，按下面的结构写。

```
H1 定制化需求
    H2 定制化需求引言
        H3 编写目的
        H3 项目背景
    H2 需求总览      表：条目 | 需求名称 | 新系统主要落点
    H2 系统对接需求
        H3 <对接系统>        正文格式：
          模块：<模块名>
          需求说明：
          <逐条说明>
    H2 功能需求
        H3 <需求名称>                ← 一级菜单本身即需求，故功能点落在 H3
            H4 业务说明 / 业务规则 / 使用角色 / 权限说明 / 功能说明 / 页面字段说明 / 输入、输出
```

**定制化需求的两个特殊约定**
1. `需求总览`表条目编号形如 `1.0`、`2.0`…，第 3 列写"新系统主要落点"（落地到产品哪个功能），用于向客户说明"定制项在标准产品里怎么落"。
2. 每个需求下可标注原文出处，固定句式：`定制需求梳理清单原始条目（第 4 部分）`。
