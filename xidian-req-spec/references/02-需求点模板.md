# 02 需求点模板（七节式）

> 本文件是规范的核心。**每个功能点（H4）下固定 7 节，顺序固定，不要调换。**
> 无内容的节可整节省略；下面标了「必有」的节不能省。
> （v1.3 起由原「四段式」改为七节式，旧四段式的槽位去向见文末对照表。）

```
H4  功能点名称（与【菜单目录】的菜单/页面一一对应，如：首页－底稿待办）
  H5 业务说明        ← 必有。叙述段落：这个功能是什么、什么业务场景下解决什么问题
  H5 业务规则        业务上的判定/流转/状态/限制/边界规则
  H5 使用角色        谁会用到这个功能（角色名清单）
  H5 权限说明        菜单权限 / 功能权限 / 列表数据权限（三要素）
  H5 功能说明        ← 必有。功能概述 + 二级页面 + 操作说明(表) + 界面原型图
  H5 页面字段说明    页面字段的含义/取值/校验/联动
  H5 输入、输出      ← 必有。输入哪些数据、输出哪些数据（两段 + 两张三列表）
```

**节与节的边界（最容易写串的三处）**

| 容易混 | 分界口径 |
|---|---|
| `业务说明` vs `功能说明` | 业务说明讲**为什么要有这个功能**（业务问题、场景、价值），功能说明讲**这个页面怎么用**（操作、交互、按钮）。不写界面细节 |
| `业务规则` vs `权限说明` | 业务规则是**业务逻辑**（什么条件成立、什么状态能做什么），权限说明是**系统授权**（谁能看到菜单、能点哪个按钮、能看哪些数据） |
| `使用角色` vs `权限说明` | 使用角色答"**谁会用到**"（含非系统角色口径，如"项目组业务人员"）；权限说明答"**系统里怎么授权**"（菜单/功能/数据范围）。**权限说明里不要再重复写"使用人员"** |
| `页面字段说明` vs `功能说明` | 功能说明写**操作**（按钮/图标/下拉），字段说明写**数据**（字段含义、取值、校验、联动） |
| `输入、输出` vs `业务说明` | 输入输出是**数据层面的进出**（数据项 + 来源/去向），不是业务背景描述 |

## 三种挂载层级（按功能点粒度选，全文档统一）

| 场景 | 结构 | 实例 |
|---|---|---|
| **单页功能点**（大多数） | `H4 功能点 → H5 七节` | `首页－底稿待办` → 业务说明/业务规则/…/输入、输出 |
| **多页模块**（一个模块下含多个并列页面） | `H4 模块 → H5 页面 → H6 七节` | `工作底稿权限维护` →（H5）`监管账号项目授权` / `授权查阅底稿管理` / … → 各带 H6 七节 |
| **定制化需求·功能需求章**（一级菜单本身即需求） | `H3 需求名 → H5 七节`（跳过 H4） | `H3 未报送统计` → H5 业务说明…（源文档即如此） |

> 实务判断：一个模块下若每个页面都要单独写权限和按钮，用"多页模块"；若整章按"一条需求一个功能点"组织（定制化需求），用 H3。
> 脚本里由 `req(..., level=)` 控制：默认 `level=4`；一级菜单即功能点传 `level=3`；多页模块传 `level=5`。

## 一、业务说明（必有）

**写法**：一段或几段普通段落（**首行缩进 2 字符**），不写"业务说明："前缀。业务语言，讲清业务场景与目的。

> ⚠️ **业务说明不加项目符号** —— 它是叙述性段落，加了圆点会被读成清单。
> 逐条列该加圆点的位置见 `04-表格与词汇库.md` 第八节。

原文示例（首页－底稿待办，原「用户场景」）：
> 为当前登录用户提供底稿待办处理，并可通过待办详情查看并处理项目的底稿任务待办。

原文示例（项目列表，多句）：
> 系统提供项目创建、删除、查询功能，以便于项目业务人员或综合管理部人员管理项目。
> 系统提供以部门维度、所有项目维度、分管项目维度的项目数据查看权限，以便于部门负责人、投行委领导可按照数据权限查看投行项目数据。

---

## 二、业务规则

**写法**：逐条列（**加项目符号**）；单条写成一行；规则本身是枚举/矩阵时用表格。

- 无：写 `无`
- 逐条：每条一句，写"什么条件下必须/不能怎样"
- 表格：如表头 `状态类型 | 状态说明`、`阶段类型 | 规则/说明`（原「状态划分」的内容就落在这里）

示例：
> 待办仅展示当前登录用户有权处理的底稿目录，无权限的目录不出现在列表中。
> 待办状态与底稿任务状态保持一致，底稿任务提交后待办自动消失。

> **原「补充说明」里的边界情况、限制条件、后续规划也写进本节**（七节式没有独立的"补充说明"节）。

---

## 三、使用角色

**写法**：逐条列角色名（**加项目符号**）；只有一条时写成一行（不加圆点）。

原文示例（项目列表）：
> 项目业务人员
> 综合管理部人员
> 部门负责人
> 投行分管领导

要点：
- 用的是**业务角色口径**（"项目业务人员""质控人员"），不是具体账号；
- 只列**这个功能点**会用到的角色 —— 与本节无关的角色不要抄；
- 本节一旦写了，`权限说明` 里**不要**再出现"使用人员：…"。

---

## 四、权限说明

**固定三要素，按其出现顺序**（缺项可省，无约束写"不涉及"）。各条**加项目符号**（只有一条时不加，写成一行）：

```
菜单权限：<谁能看到这个菜单>
功能权限：维护－包括：新建、下载样本、导入项目、查询、项目详情。可支持按照系统角色进行授权…
          查看－包括：查询、项目详情。…
          删除－…
列表数据权限：<能看哪些数据，按角色分别写>
```

**单角色时写成一行**（原文）：
> 菜单权限：登录用户均有首页权限
> 功能权限：不涉及
> 列表数据权限：所有需要当前登录用户处理的底稿目录

**多角色时标签独占一行、随后逐条列角色**（原文 · 项目列表）：
> 菜单权限：
> 我的项目－普通业务人员拥有该菜单权限。
> 本部门项目管理－作为部门负责人拥有该菜单权限。
> 所有项目管理－作为投行分管领导、质控领导等拥有该菜单权限。
> 功能权限：
> 维护－包括：新建、下载样本、导入项目、查询、项目详情。可支持按照系统角色进行授权，需要满足给到菜单权限的人可进行维护。
> 查看－包括：查询、项目详情。支持给到菜单权限的人员可查看项目列表信息，通过查询条件进行查询。
> 列表数据权限：
> 我的项目－作为项目成员可查看项目信息
> …

**角色 × 状态矩阵**（当权限随项目状态变化时补一张表，放在本节末尾）：
表头 `角色/项目状态 | 正常 | 终止 | 完成`，单元格填可执行的动作，不可执行填 `/`。

> ⚠️ **不要写"使用人员"** —— 已由上一节「使用角色」承担，重复写会出现两处不一致。

## 五、功能说明（必有）

**四个子要素，顺序固定**：`功能概述 → 二级页面 → 操作说明 → 界面原型图`。没有的跳过。

> 脚本里 `功能说明` 收 4 种形态：字符串/一维列表 → 当「功能概述」；二维列表 → 当「操作说明」表；
> dict → 按 4 个子要素取。

### 5.1 功能概述
叙述段落（**首行缩进 2 字符**，不加圆点）：这个页面是干什么用的、有哪几块、怎么进入。

### 5.2 二级页面
一个菜单下挂多个并列页面时才用。固定格式 `二级页面：` + 表 `二级页面 | 规则/说明`。

> `二级页面` 非源文档固有小节名，是整理"一个菜单下挂多个并列页面"时的规范写法。

### 5.3 操作说明（★ 最核心）
固定格式：先写一行 `操作说明：`，紧跟一张三列表：

| 名称 | 类型 | 规则/说明 |
|---|---|---|
| 待办详情－待办 | 按钮 | 点击后进入对应项目的需提交待办详情页 |
| 提交 | 按钮 | 勾选需要提交的底稿目录，点击提交按钮可进行提交操作 |
| 更多操作 | 下拉选择 | 可进行底稿目录索引、附件引用、引用流程、引用底稿、填写说明的操作 |
| 更多 | 下拉选择 | 可进行下载、预览的操作 |
| 删除 | 按钮 | 上传后未提交的文件可进行删除的操作 |

要点：
- **排布顺序 = 页面视觉顺序**：工具条按钮 → 搜索区 → 列表"操作列"图标 → 弹窗内按钮；
- `名称` 用界面上的原始文案；同一名称出现在不同位置时加位置前缀（`操作列－删除`、`待办详情－待办`）；
- `规则/说明` 写交互结果，不写技术实现；有弹窗/二次确认要写明（"弹出框询问用户是否删除"）；
- 表格数量随需求复杂度变化，常见 2~29 行；
- **脚本会自动补表头**，只写数据行即可。

### 5.4 界面原型图
固定写法：`界面原型图：` 或 `界面原型图` 单独一行，随后插入页面截图（多张时每张上方用"列出段落1"样式写图注，如 `快捷操作图标：`、`我的借阅页面：`）。
无图时写 `界面原型图：无`。

## 六、页面字段说明

**写法**：表 `字段名称 | 规则/说明`（脚本自动补表头）；字段少且简单时逐条列或一行。

- 无：写 `不涉及`
- 表：逐个字段写含义、取值范围、校验、联动
- 需要区分"含义"和"校验"时可用 `字段名称 | 字段说明` + `字段名称 | 规则/说明` 两张表

示例：
| 字段名称 | 规则/说明 |
|---|---|
| 待办数量 | 统计当前用户待处理底稿目录数，"0" 时置灰并显示"暂无待办" |
| 截止时间 | 取底稿任务的计划完成时间，超过当天 24:00 显示为红色 |

> 原「字段说明」与「字段逻辑」在本节**合并**：字段含义与取值/校验规则写在同一条里。

---

## 七、输入、输出（必有）

**写法**：两段 + 两张三列表。写清**这个功能点输入哪些数据、输出哪些数据**。

```
输入：
  表  数据项 | 来源 | 说明
输出：
  表  数据项 | 去向 | 说明
```

| 段 | 表头 | 写什么 |
|---|---|---|
| 输入 | `数据项 \| 来源 \| 说明` | 这个功能点**运行需要**哪些数据：数据叫什么、从哪来、怎么取 |
| 输出 | `数据项 \| 去向 \| 说明` | 这个功能点**产生或改变**哪些数据：数据叫什么、写到哪去、产生什么后果 |

**来源 / 去向的用词口径**（沿用 04 的词表，同一份文档内统一）：

| 用词 | 什么时候用 |
|---|---|
| `人工录入` | 页面上由人填写/勾选的 |
| `<系统名>对接` | 从别的系统同步来的，如 `投行项目管理系统对接`、`底稿系统推导` |
| `系统推导` | 由系统按已有数据和规则算出来的（非人工、非对接） |
| `参数配置` | 来自基础维护/配置菜单里配好的参数 |
| `导入文件` | 通过 Excel/模板批量导入的 |
| `去向：<页面/模块>` | 写到本系统某个页面/模块，如 `去向：底稿详情页` |
| `去向：<外部系统>` | 推送给别的系统，如 `去向：投行项目管理系统` |
| `去向：文件导出` | 生成 Excel/PDF 等文件给用户下载 |
| `去向：系统日志` | 只落留痕，不产生业务数据 |

示例：

```
输入：
| 数据项 | 来源 | 说明 |
| 待处理底稿目录 | 底稿系统推导 | 按当前登录用户的底稿权限过滤 |
| 底稿任务计划完成时间 | 底稿详情页人工录入 | 用于待办排序与超期标红 |

输出：
| 数据项 | 去向 | 说明 |
| 已提交底稿目录 | 去向：底稿详情页 | 提交后写入项目底稿目录，状态改为"已提交" |
| 待办处理留痕 | 去向：系统日志 | 记录处理人、处理时间与动作 |
```

> **与旧「数据来源」的区别**：旧写法只回答"数据从哪来"，是单向的；
> 本节要求**成对**写清流入与流出 —— 这是七节式相对四段式最实质的补强，评审时能直接对上接口清单。
> 数据项很少时允许退化成项目符号，但**来源/去向必须写清**，否则这一节没有价值。

## 八、完整范例（可直接照抄结构）

**H4 首页－底稿待办**

`H5 业务说明`
> 为当前登录用户提供底稿待办处理，并可通过待办详情查看并处理项目的底稿任务待办。

`H5 业务规则`
> 待办仅展示当前登录用户有权处理的底稿目录，无权限的目录不出现在列表中。
> 待办状态与底稿任务状态保持一致，底稿任务提交后待办自动消失。

`H5 使用角色`
> 项目业务人员
> 项目负责人
> 质控人员

`H5 权限说明`
> 菜单权限：登录用户均有首页权限
> 功能权限：不涉及
> 列表数据权限：所有需要当前登录用户处理的底稿目录

`H5 功能说明`
> 首页以待办卡片形式汇总当前用户的底稿任务，点击可进入待办详情逐项处理。（功能概述）
> 操作说明：
> （表：名称|类型|规则/说明）
> 界面原型图：
> （截图）

`H5 页面字段说明`
> （表：字段名称|规则/说明）

`H5 输入、输出`
> 输入：（表：数据项|来源|说明）
> 输出：（表：数据项|去向|说明）

---

**H4 项目列表**（复杂型 · 权限矩阵 + 规则表 + 明细表 + 字段表 + 输入输出）

- `业务说明`：三句（项目增删查 + 三种数据维度 + 监管授权）
- `业务规则`：与投行对接的状态保持一致 + `状态类型|状态说明` 表（正常/完成/终止）
- `使用角色`：项目业务人员 / 综合管理部人员 / 部门负责人 / 投行分管领导
- `权限说明`：菜单权限 4 条（我的项目/本部门/所有项目/分管项目）+ 功能权限 3 档（维护/查看/删除）+ 列表数据权限
- `功能说明`：功能概述 + `操作说明` 表（新建/查询/收起展开/下载样本/导入/删除/查看详情）+ 界面原型图
- `页面字段说明`：`字段名称|规则/说明` 表
- `输入、输出`：输入 = 投行项目信息（对接）、项目人员（人工录入）；输出 = 项目台账（去向：项目管理）、监管授权记录（去向：系统日志）

## 九、与旧「四段式」的对照（v4.0.5 及更早文档用四段式）

> ⚠️ **同一份文档内不要混用两种结构**。并入既有主文档时，先确认主文档按哪套写，再决定是否回切。

| 旧四段式槽位 | 七节式去向 |
|---|---|
| H5 用户场景 | → `业务说明`（内容可平移，口径更偏"业务背景 + 解决什么问题"） |
| H5 权限说明 | → `权限说明`（**去掉"使用人员"**，角色移到 `使用角色`） |
| H5 功能描述 · 数据来源 | → `输入、输出` 的**输入表「来源」列**（不再单列小节） |
| H5 功能描述 · 状态划分 | → `业务规则`（状态枚举属业务规则） |
| H5 功能描述 · 二级页面 | → `功能说明` 的「二级页面」子要素（不变） |
| H5 功能描述 · 操作说明 | → `功能说明` 的「操作说明」子要素（不变） |
| H5 功能描述 · 界面原型图 | → `功能说明` 的「界面原型图」子要素（不变） |
| H5 功能描述 · 字段说明 / 字段逻辑 | → `页面字段说明`（两者合并为一节） |
| H5 补充说明 | → `业务规则`（边界情况、限制条件、后续规划） |

实测词频参考（v4.0.5，四段式）：`用户场景` 67 次、`功能描述` 60 次、`权限说明` 59 次、`补充说明` 46 次。
偶见用 `功能权限`/`功能说明` 代替 `权限说明`/`功能描述`，同一份文档内应统一。
